STATUS: VALIDATED (Phase 00) — every statement about current code was checked
against the sources on branch `claude/vaelen-master-prompt-aw7zqj`; items marked

Scope: the engine-agnostic simulation kernel (`Source/VaelenCore`, and every

## 1. Language and toolchain

| Item | Rule | Where it is set |
|---|---|---|
| Standard | C++20, no compiler extensions | `CMakeLists.txt` (`CMAKE_CXX_EXTENSIONS OFF`), `*.Build.cs` / `*.Target.cs` (`CppStandardVersion.Cpp20`) |
| Exceptions | Disabled | `-fno-exceptions`, MSVC `_HAS_EXCEPTIONS=0`, UBT `bEnableExceptions = false` |
| RTTI | Disabled | `-fno-rtti`, MSVC `/GR-`, UBT `bUseRTTI = false` |
| PCH / unity | None in the kernel | `VaelenCore.Build.cs` (`NoPCHs`, `bUseUnity = false`) |
| Warnings (GCC/Clang) | `-Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion -Wold-style-cast -Wcast-align -Wnon-virtual-dtor -Woverloaded-virtual -Wnull-dereference -Wdouble-promotion -Wformat=2`, `-Werror` | `vaelen_build_flags` in `CMakeLists.txt` |
| Warnings (MSVC) | `/W4 /permissive- /utf-8`, `/WX` | same |
| Definitions (headless) | `VAELENCORE_API=` (empty), `VAELEN_HEADLESS_BUILD=1`, `VAELEN_ASSERTS_ENABLED=0/1` | `CMakeLists.txt`, option `VAELEN_ENABLE_ASSERTS` (default ON) |
| Definitions (UBT) | `VAELEN_UNREAL_BUILD=1`; `VAELENCORE_API` generated by UBT | `VaelenCore.Build.cs` |

Every kernel and test file must compile warning-free with both `clang++` and
`g++` (CI also builds MSVC and AppleClang, see section 12). Practical
consequences of the flag set:

- Every narrowing or sign change is an explicit `static_cast`; C-style casts
  are an error (`-Wold-style-cast`).
- No implicit `float` → `double` promotion: use `f` literals and hex-float
  constants (`0x1.0p-24f`) as `Random.cpp` does.
- No shadowing: constructor parameters that initialise a member of the same
  name take an `In` prefix (`InName`, `InState`, `InValue`).
- Polymorphic classes have a virtual destructor (`ILogSink`).

## 2. Formatting

Source of truth: `.editorconfig` and `.clang-format`, as applied in the
checked-in code.

- **Braces**: Allman on every block, including single-statement `if`/`for`
  bodies (`AllowShortIfStatementsOnASingleLine: Never`,
  `AllowShortLoopsOnASingleLine: false`). Braces are never omitted.
- **Indentation**: tabs, tab width 4, for `.h .hpp .cpp .inl .cs`. Spaces
  (2) for Markdown, YAML, JSON, CMake, Python, shell.
- **Line length**: 120 columns.
- **Namespaces**: the body of a namespace is indented one tab and closed with
  `} // namespace Vaelen` (anonymous: `} // namespace`).
- **Access specifiers**: at the same column as `class` (`AccessModifierOffset: -4`).
- **Pointers/references**: bind left, `const char* Name`, `const State& InState`.
- **Templates**: `template <typename T>` on its own line, space after
  `template`.
- **Short functions**: one-line bodies are allowed only for inline member
  functions (`bool IsEnabled(LogLevel Level) const noexcept { return Level >= MinLevel; }`).
- **Preprocessor**: nested directives indent the keyword after `#` with a tab
  (`#	define`, `#	if`), as in `Assert.h` and `Log.h`.
- **Includes**: not sorted by the formatter (`SortIncludes: false`); ordered
  by hand as described in section 4.
- **Encoding**: UTF-8, LF line endings, final newline, no trailing whitespace.
- **Comments**: `///` for API documentation on declarations, `///<` trailing
  on fields and enumerators, `//` for implementation notes. Section rulers of
  the form `// ── Draws ──…` are optional.

Formatter caveat (measured 2026-09-05 with clang-format 18, dry run): the
checked-in `.clang-format` does not reproduce the checked-in code. It sets
`NamespaceIndentation: None` and no `IndentPPDirectives`, so applying it would
strip the namespace-body indentation and the `#	define` nesting described above
(68–396 changed lines per kernel file). With those two keys changed to
`NamespaceIndentation: All` and `IndentPPDirectives: AfterHash` the same
formatter reproduces every kernel file to within 0–10 lines (one-line inline
functions only). Until `.clang-format` is corrected, the existing kernel files
are the style reference; do not reformat whole files with the checked-in
configuration.

## 3. Naming

PascalCase everywhere, no Hungarian notation, no Unreal type prefixes inside
the kernel.

| Entity | Convention | Examples (from code) |
|---|---|---|
| Namespaces | PascalCase; kernel code lives in `Vaelen` | `Vaelen`, `Vaelen::Log`, `Vaelen::Detail`, `Vaelen::HashConstants`, `VaelenTest` |
| Types, enums, aliases | PascalCase | `RandomStream`, `PersistentId`, `IdKind`, `Hash64`, `AssertHandler` |
| Fundamental aliases | lowercase, mirror the builtin names — the only lowercase types | `int8 … int64`, `uint8 … uint64`, `usize` (`CoreTypes.h`) |
| Functions, methods | PascalCase verbs; `Get`/`Set` accessors; `Is`/`Has` predicates | `Allocate`, `Derive`, `NextU64`, `GetState`, `IsValid` |
| Parameters, locals, members | PascalCase; no `m_` / trailing `_` | `Count`, `MinLevel`, `State` |
| Ctor parameter initialising a same-named member | `In` prefix | `InName`, `InMinLevel`, `InState` |
| Loop counters | short lowercase `i`, `j` or single capitals are both in use | `Hash.h`, `Random.cpp` |
| File-scope statics (internal linkage) | `G` prefix, inside an anonymous namespace | `GHandler`, `GFailureCount`, `GGlobalMinLevel` |
| Constants | PascalCase, `inline constexpr` at namespace scope or `static constexpr` in a class; no `k` prefix, no ALL_CAPS | `MaxSinks`, `Fnv1a64Offset`, `PersistentId::SerialBits` |
| Macros | `VAELEN_` prefix, UPPER_SNAKE; test macros `VT_` and `VAELEN_TEST` | `VAELEN_CHECK`, `VAELEN_LOG_INFO`, `VT_CHECK_EQ` |
| Interfaces | `I` prefix, pure virtual, virtual destructor; leaf classes `final` | `ILogSink`, `StdioLogSink final` |
| Enumerations | `enum class Name : uint8` (or another fixed width); PascalCase enumerators; explicit values when part of a save format | `IdKind`, `LogLevel`, `AssertKind` |
| Log categories | `Log` + domain | `LogCore` (kernel), `LogVaelen` (Unreal) |
| Implementation helpers exposed in headers | `Vaelen::Detail` | `Detail::ReportAssert`, `Detail::EnsureResult` |
| User-defined literals | `_v<name>` (one instance so far) | `"hydrology"_vhash` |
| Files | PascalCase; header and source share a stem; tests `Test_<Suite>.cpp`; Unreal-facing `<Module>Module.cpp` | `Random.h` / `Random.cpp`, `Test_Random.cpp`, `VaelenCoreModule.cpp` |

Unreal modules (`Source/Vaelen`) follow Unreal conventions instead: `F`/`U`/`A`/`T`/`E`
prefixes (`FVaelenModule`, `FVaelenLogSink`), `DECLARE_LOG_CATEGORY_EXTERN`,
`UE_LOG`. Those prefixes never appear in kernel code.

## 4. File layout

### 4.1 Header (`Source/<Module>/Public/Vaelen/<Area>/<Name>.h`)

```cpp
// VAELEN - VaelenCore
// One-line purpose of the file.
//
// STATUS: VALIDATED (Phase 00)
//
// Design notes: rules, layout, rationale, references to the master prompt.
#pragma once

#include "Vaelen/Core/CoreTypes.h"
#include "Vaelen/Core/Hash.h"

#include <array>
#include <compare>

namespace Vaelen
{
	/// API documentation.
	class VAELENCORE_API IdAllocator
	{
	public:
		...
	private:
		State Current;
	};
} // namespace Vaelen
```

Rules, all enforced by `Tools/check_kernel_purity.py` unless stated otherwise:

1. Line 1 is the project banner `// VAELEN - <Module>`; line 2 the purpose.
2. A `// STATUS: <VALIDATED|PROTOTYPE|INCOMPLETE|UNVERIFIED>` line appears in
   the banner comment (rule R5); anything after the value is free text, e.g.
   `(Phase 00)` or `- covered by Tests/Core/Test_Log.cpp`.
3. `#pragma once` (R5), no include guards.
4. Includes in two blocks separated by a blank line: `"Vaelen/..."` headers
   first, then standard headers in `<...>`, alphabetical within the block
   (convention, not tool-checked). Nothing else may be included (R1); the
   angle form `<Vaelen/...>` is rejected.
5. Exported classes and out-of-line free functions carry `VAELENCORE_API`
   (empty in the headless build). `constexpr`/`inline` functions defined in
   the header may omit it (`Hash.h` does; `Version.h` keeps it on
   `GetSaveFormatVersion`; both forms compile).
6. One topic per header: a header holds one main type plus the small types
   that only make sense with it (`Ids.h`: `IdKind`, `PersistentId`,
   `IdAllocator`, `std::hash<PersistentId>`). Do not merge unrelated systems.
7. Everything lives in `namespace Vaelen`; a `std` specialisation is the only
   thing allowed outside it (`std::hash<PersistentId>`).

### 4.2 Source (`Source/<Module>/Private/<Name>.cpp`)

```cpp
// VAELEN - VaelenCore
#include "Vaelen/Core/Ids.h"
#include "Vaelen/Core/Assert.h"

namespace Vaelen
{
	namespace
	{
		// internal-linkage helpers and G-prefixed statics
	} // namespace

	...
} // namespace Vaelen
```

- The file's own header is included first, then other `Vaelen/` headers, then
  standard headers after a blank line.
- A `STATUS` line is optional in `.cpp` files (only `Log.cpp` carries one
  today); when present it is validated (R5) and, if `VALIDATED`, subject to the
  no-fake-done rule (R6). Prefer adding it.
- `<Module>Module.cpp` is the single Unreal-facing translation unit of a kernel
  module (R0): it may include Unreal headers, is excluded from the CMake build,
  and is labelled `STATUS: UNVERIFIED` because CI cannot compile it.

### 4.3 Test file (`Tests/<Module>/Test_<Suite>.cpp`)

```cpp
// VAELEN - VaelenCore tests
// What this suite covers, one paragraph.
//
// STATUS: VALIDATED
#include "VaelenTest.h"

#include "Vaelen/Core/Random.h"

#include <vector>

using Vaelen::RandomStream;   // explicit using-declarations (Test_Random, Test_Hash,
using Vaelen::uint64;         // Test_Assert, Test_Version) or `using namespace Vaelen;`
                              // (Test_Ids, Test_Log); either is accepted in tests, never in the kernel

VAELEN_TEST(Random, DeriveByName)
{
	...
}
```

Six of the seven existing suites follow this banner; `Test_Harness.cpp` has a
one-line banner and no STATUS line. Test files are not scanned by the purity
checker but follow the same formatting and naming rules and compile with the
same warning flags.

## 5. Kernel purity

"The kernel" is every module named in `Tools/kernel_modules.txt` (today:
`VaelenCore`). The same files are compiled by UBT inside the UE5 project and by
CMake without any engine, so they must be pure standard C++20. The rules below
are enforced textually by the CTest entry `Kernel.Purity` (section 13); the
compiler flags enforce the rest.

### 5.1 Includes (R1)

Allowed: `"Vaelen/..."` headers and C/C++ standard headers only. No engine,
OS or third-party header. Standard headers banned in the kernel:

| Banned | Reason (as reported by the checker) |
|---|---|
| `<random>` | non-deterministic / implementation-defined randomness; use `Vaelen/Core/Random.h` |
| `<chrono>`, `<ctime>`, `<time.h>` | wall-clock time is non-deterministic; simulation time is part of the world state |
| `<iostream>`, `<istream>`, `<ostream>`, `<iomanip>`, `<ios>`, `<fstream>`, `<sstream>`, `<strstream>`, `<syncstream>`, `<spanstream>`, `<streambuf>` | stream I/O is heavy and locale-dependent; the kernel formats with `<cstdio>` |
| `<locale>`, `<clocale>`, `<locale.h>`, `<codecvt>` | locale-dependent behaviour makes formatting platform-dependent |
| `<exception>`, `<stdexcept>` | exception machinery in a kernel built with `-fno-exceptions` |
| `<typeinfo>`, `<typeindex>` | RTTI in a kernel built with `-fno-rtti` |
| `<csetjmp>`, `<setjmp.h>` | non-local jumps are exceptions in disguise |
| `<filesystem>` | OS file-system access does not belong in the simulation kernel |

`<cstdio>`, `<cstdarg>`, `<atomic>`, `<mutex>` and `<thread>` are allowed.

### 5.2 No exceptions, no RTTI (R2, R3)

No `throw`, `try`, `catch`, `dynamic_cast`, `typeid`. Failure is reported
through return values (`bool`, `PersistentId::Invalid()`, a default value) plus
an assertion when the failure is a programming error (section 8). Virtual
dispatch through explicit interfaces is fine; type identification through RTTI
is not.

### 5.3 Fixed-width integers (R7)

Use `int8/16/32/64`, `uint8/16/32/64` and `usize` from `CoreTypes.h`. Bare
`long`, `unsigned long`, `long long` are rejected except inside a
`static_cast<...>`, which is the sanctioned form at `printf` boundaries
(`static_cast<long long>(Value)` with `%lld`, `static_cast<unsigned long long>`
with `%llu`). Plain `int` appears only where the C library dictates it
(`vsnprintf` return values), for shift counts and for local loop counters in
private code; public kernel APIs use fixed-width types (`int32 Line`,
`uint64 Seed`). Enumerations declare a fixed underlying type.

### 5.4 Globals and static state

No global object with dynamic initialisation may influence simulation results.
Simulation state lives in explicit, serialisable, caller-owned structs
(`RandomStreamState`, `IdAllocator::State`); nothing in the kernel hides state
in a static. The statics that do exist are infrastructure only:

- `std::atomic` globals in anonymous namespaces (constant-initialised):
  assertion handler, failure counter, global log level, dispatch counter.
- Function-local statics for the log sink table and its mutex (`Log.cpp`).
- `LogCategory` objects (`LogCore`, categories created with
  `VAELEN_DEFINE_LOG_CATEGORY`). The constructor is not `constexpr`, so these
  are ordinary namespace-scope objects; they only hold a name and a threshold.

A simulation system must never read these to make a decision.

### 5.5 `constexpr`, `noexcept`, `[[nodiscard]]`

- Pure functions are `constexpr` (`HashBytes`, `Mix64`, `HashCombine`,
  every `PersistentId` member, `GetSaveFormatVersion`, `ToUnderlying`).
- Constants are `inline constexpr` (namespace) or `static constexpr` (class).
- Every kernel function that cannot fail is `noexcept`; with exceptions
  disabled this is documentation, and it is applied consistently
  (`RandomStream`, `IdAllocator`, `Log::*` accessors). Variadic reporting
  functions (`Log::Write`, `Detail::ReportAssertF`) are the exception.
- `[[nodiscard]]` is not used in Phase 00 code; it is allowed.

### 5.6 Threading

Simulation objects are single-threaded by design (`IdAllocator`: "Not
thread-safe by design: allocation happens on the simulation thread in a
deterministic order"). Logging and assertion reporting are thread-safe
(atomics, one mutex around the sink table). Multithreading inside the
simulation is *planned* (master prompt §4) and must keep results independent
of scheduling.

## 6. Determinism rules

Master prompt §35: same seed + same inputs = same result. The kernel provides
the primitives; every later system must follow these rules.

1. **Randomness comes only from `Vaelen::RandomStream`.** `rand()`,
   `std::random_device`, `<random>` engines and every OS clock are rejected
   (R1/R4). The generator is xoshiro256** seeded through SplitMix64; the
   sequence for a given seed is frozen by known-answer tests
   (`Test_Random.cpp`, `Test_Hash.cpp` "frozen values").
2. **One stream per system, derived by name.** From the world root stream,
   each system derives its own child with `Derive("hydrology")`; per-instance
   streams use `Fork(Index)`. Derivation depends only on the parent's *root
   seed* and never advances the parent, so adding a draw in one system cannot
   perturb another. Never share a stream between systems; never draw from a
   stream in an order that depends on scheduling.
3. **Stream state is world state.** `RandomStreamState` (seed, 4 words,
   `DrawCount`) is saved and restored verbatim; `Jump()` is for non-overlapping
   sub-sequences when hierarchical derivation does not apply.
4. **No wall-clock time.** Simulation time is a value in the world state
   (*planned*: Phase 01 simulation clock). `<chrono>`, `time()`, `clock()`
   and friends are rejected.
5. **Persistent identity comes from `IdAllocator`.** Ids are monotonic per
   kind, never reused, allocated on the simulation thread in a deterministic
   order; the allocator's counters are saved with the world. `IdKind` values
   are append-only.
6. **Hashing is frozen.** FNV-1a 64, `Mix64` and `HashCombine` feed stream
   derivation and map keys; changing them changes every derived stream, which
   `Test_Hash.cpp` guards with frozen regression values.
7. **Iteration order** (*policy, not yet tool-enforced; no such container
   exists in the kernel today*): never iterate an unordered container or order
   anything by pointer value when the result touches world state. Iterate
   arrays/vectors by index, or keyed containers by `PersistentId`.
8. **Sorting** (*policy*): use a stable sort with a total, deterministic key
   (tie-break on `PersistentId`). No sort exists in the kernel yet;
   `std::sort` appears only in tests, on values.
9. **Floating point** (*policy*): authoritative state prefers integers /
   fixed point. `NextDouble()`/`NextFloat()` are derived from integer bits and
   are bit-identical everywhere; `NextNormal()`, `RangeDouble()` and `Chance()`
   involve `<cmath>` or floating arithmetic, and `std::log` is not guaranteed
   to be correctly rounded across libm implementations, so cross-platform
   bit-exactness is not promised for them. Do not accumulate floating-point
   values across ticks for authoritative quantities unless the header
   documents why and how it is bounded. The headless build compiles the
   kernel with `-ffp-contract=off` (GCC/Clang) and `/fp:precise` (MSVC) so
   that no fused multiply-add is introduced by one compiler and not another
   (ADR-0009); the Unreal build must be configured the same way before any
   floating-point result is called cross-compiler deterministic.
10. **Logging and assertions never change state.** See sections 7 and 8.

*Planned* (master prompt §35, Phases 01 and 16): event logs, replay and
checkpoints built on the above.

## 7. Logging

Header: `Vaelen/Core/Log.h`. printf-style, category-based, pluggable sinks.

### 7.1 Categories

```cpp
// in a header of the owning module
VAELEN_DECLARE_LOG_CATEGORY(LogEconomy);

// in exactly one .cpp
VAELEN_DEFINE_LOG_CATEGORY(LogEconomy);                 // MinLevel = Info
VAELEN_DEFINE_LOG_CATEGORY_LEVEL(LogEconomy, Debug);   // explicit threshold
```

Categories are `Vaelen::LogCategory` objects named `Log<Domain>`. The kernel
defines `LogCore` (threshold `Trace`). Each domain module declares its own.

### 7.2 Levels

Numeric order and mechanics are code facts; the "use for" column is the
project convention.

| Level | Value | Mechanics | Use for |
|---|---|---|---|
| `Trace` | 0 | compiled out in UE Shipping (`VAELEN_LOG_COMPILED_MIN_LEVEL` = Info there, Trace elsewhere) | per-call / per-tick detail |
| `Debug` | 1 | compiled out in UE Shipping | developer diagnostics |
| `Info` | 2 | default category threshold | rare lifecycle milestones (module start, world created) |
| `Warning` | 3 | `StdioLogSink` writes to stderr from here up | recoverable anomaly worth a human look |
| `Error` | 4 | assertion failures are logged here by the default handler | failure that needs attention |
| `Fatal` | 5 | just a record; logging at Fatal does not abort (`Log.FatalLevelIsJustARecord`) | last words before the assertion machinery stops the process |
| `Off` | 6 | threshold value only | never log at `Off` |

### 7.3 Writing records

```cpp
VAELEN_LOG_INFO(LogEconomy, "market %s opened with %llu goods", Name, static_cast<unsigned long long>(Count));
```

- Macros `VAELEN_LOG_TRACE/DEBUG/INFO/WARNING/ERROR/FATAL(Category, Format, ...)`.
- Filtering order: compile-time floor → `Category.IsEnabled(Level)` →
  `Log::GetGlobalMinLevel()`. Format arguments are only evaluated when the
  record passes all three.
- Formatting is `vsnprintf` into a 2048-byte buffer; longer messages are
  truncated silently. Format strings are checked by the compiler
  (`VAELEN_PRINTF_ATTR`, `-Wformat=2`): pass `int64/uint64` through
  `static_cast<long long>` / `static_cast<unsigned long long>`.
- **Hot loops**: the three checks are cheap but a delivered record takes the
  sink mutex and calls every sink. Inside inner simulation loops either log at
  `Trace`/`Debug` behind an explicit `if (LogX.IsEnabled(LogLevel::Trace))`
  hoisted out of the loop, or aggregate and log once per tick.
- **Logging never affects state**: no simulation code branches on whether a
  record was delivered; `Log::GetDispatchedRecordCount()` exists for tests.

### 7.4 Sinks

- Implement `ILogSink::Write(const LogRecord&)` (and optionally `Flush()`).
- Sinks are not owned by the log system: `AddSink` (returns `false` when
  null or when the table of 8 is full, `true` when already registered),
  `RemoveSink` before the sink is destroyed, `RemoveAllSinks`, `Flush`.
- Sinks are called under a non-recursive mutex, so a sink need not be
  thread-safe, but **a sink must never log** (it would re-enter the mutex).
- The headless test runner installs `StdioLogSink` only with `--verbose`;
  the Unreal module installs `FVaelenLogSink`, which maps kernel levels onto
  `UE_LOG` verbosities.

## 8. Assertions

Header: `Vaelen/Core/Assert.h`. Enabled when `VAELEN_ASSERTS_ENABLED` is 1.
CMake always defines it from the option `VAELEN_ENABLE_ASSERTS` (default ON,
independent of build type). When the build system does not define it (UBT does
not), `Assert.h` derives it: 0 in an Unreal Shipping build or when `NDEBUG` is
defined, else 1.

| Macro | Condition evaluated when disabled | Fatal | Yields | Use for |
|---|---|---|---|---|
| `VAELEN_CHECK(Expr)` | no | yes (default handler aborts) | – | invariants and preconditions whose violation is a programming error |
| `VAELEN_CHECKF(Expr, Fmt, ...)` | no | yes | – | same, with a printf message (1024-byte buffer) |
| `VAELEN_VERIFY(Expr)` | **yes** (always evaluated) | yes when enabled | – | expressions with side effects that must run in every build (`VAELEN_VERIFY(Log::AddSink(&Sink))`) |
| `VAELEN_ENSURE(Expr)` | **yes**, exactly once | no; every failure is reported | `bool` | recoverable conditions: `if (!VAELEN_ENSURE(Ptr != nullptr)) { return; }` |
| `VAELEN_UNREACHABLE()` | – | always aborts, even when assertions are disabled | – | code paths that must never execute |

Rules:

- A `CHECK` condition must have no side effects (it is not evaluated when
  disabled).
- **Check, then guard.** After a `CHECK` the code must still behave safely
  when assertions are disabled or the handler returns, because the test
  harness installs a returning handler: `IdAllocator::Allocate` checks the
  kind and then returns `Invalid()`; `RandomStream::Below(0)` checks and
  returns 0. Never rely on the abort.
- Handler: `SetAssertHandler(Handler, UserData)`; `nullptr` restores the
  default, which logs at `Error` on `LogCore`, flushes and aborts for `Check`.
  Handlers receive an `AssertInfo` (kind, expression text, file, line,
  function, message). `GetAssertFailureCount()` counts every report.
- The Unreal module routes `Ensure` to `ensureAlwaysMsgf` and `Check` to
  `UE_LOG(..., Fatal, ...)`; the tests use `VaelenTest::ScopedAssertCapture`.
- Assertions never modify state; they report and (possibly) stop.

## 9. STATUS labels and the no-fake-done rule

Master prompt §63 defines three labels; the checker accepts a fourth for code
that this environment cannot compile.

| Label | Meaning | Obligations |
|---|---|---|
| `VALIDATED` | Compiles warning-free with clang and gcc, tests pass, behaviour reviewed | No `TODO`, `FIXME` or "implement later" anywhere in the file (R6) |
| `PROTOTYPE` | Works for a narrow case; API and behaviour may change | Say what is covered and what is not |
| `INCOMPLETE` | Known missing parts | List the gaps in the banner |
| `UNVERIFIED` | Could not be compiled or run here (Unreal-facing files) | Say why (`- not compiled in the headless CI (requires UE5)`) |

- Every header carries a STATUS line (R5); `.cpp`, test files and tools carry
  one by convention.
- Never present a stub as finished. A placeholder must be labelled
  `PROTOTYPE` or `INCOMPLETE`, and the missing behaviour must be visible in
  the header comment, not hidden in a `TODO` inside a `VALIDATED` file.
- Never claim a test was run when it was not (master prompt §67). Progress
  reports list the exact commands and their results.
- A system is promoted to `VALIDATED` only after the tests required in
  section 10 exist and pass on both compilers.

## 10. Tests

### 10.1 Layout and naming

- Harness: `Tests/Harness/VaelenTest.h` (macros, registry,
  `ScopedAssertCapture`) and `Tests/Harness/TestMain.cpp` (runner). No
  external framework, no exceptions, no RTTI.
- One executable per kernel module: `Tests/<Module>/CMakeLists.txt` globs
  `Test_*.cpp` (today `Tests/Core` → `VaelenCoreTests`).
- **File = suite = CTest entry**: `Tests/Core/Test_Random.cpp` registers tests
  with `VAELEN_TEST(Random, Name)` and becomes CTest entry `Core.Random`, which
  runs `VaelenCoreTests --suite Random`. If the suite name in the macro does
  not match the file stem, the CTest entry matches zero tests and fails with
  exit code 3.
- Test names are PascalCase sentences describing the property
  (`DeterminismSameSeedIdenticalDifferentSeedsDiffer`,
  `AllocatorExhaustionTriggersCheck`).

### 10.2 Macros

| Macro | Behaviour |
|---|---|
| `VT_CHECK(Expr)` | records a failure, continues |
| `VT_CHECK_MSG(Expr, Fmt, ...)` | same, with a printf detail |
| `VT_REQUIRE(Expr)` | records a failure and returns from the test |
| `VT_CHECK_EQ(Actual, Expected)` / `VT_REQUIRE_EQ` | equality with both values printed (integers, enums, bools, floats, pointers) |
| `VT_CHECK_NE(Actual, NotExpected)` | inequality |
| `VT_CHECK_STREQ(Actual, Expected)` | C-string equality, null-safe |
| `VT_CHECK_NEAR(Actual, Expected, Tolerance)` | absolute tolerance on doubles |
| `VaelenTest::ScopedAssertCapture` | RAII: routes `VAELEN_CHECK/ENSURE` reports to counters (`CheckCount`, `EnsureCount`, `LastExpression`, `LastMessage`) instead of aborting; restores the default handler on destruction |

Compare fixed-width values against literals of the same type
(`VT_CHECK_EQ(Stream.NextU64(), uint64{11520})`) so `-Wsign-conversion` stays
quiet.

### 10.3 Rules for tests

- Tests are independent and order-agnostic. Registration order is preserved
  within a translation unit but unspecified across files; a test never relies
  on another test having run.
- Restore every global you touch: remove sinks, restore
  `Log::SetGlobalMinLevel`, let `ScopedAssertCapture` go out of scope.
- Deterministic by construction: fixed seeds, statistical tolerances chosen
  far outside sampling noise and justified in a comment (see
  `Test_Random.cpp`), no timing-based assertions. The only threaded test
  (`Log.ConcurrentWritesFromEightThreads`) asserts counts, not ordering.
- Assertion paths: wrap in `ScopedAssertCapture`, guard with
  `#if VAELEN_ASSERTS_ENABLED`, and test the compiled-out contract in the
  `#else` branch (`Test_Assert.cpp`).
- Tests may use the full standard library (`<thread>`, `<unordered_map>`,
  `<vector>`, …); they are not scanned by the purity checker but must compile
  with the same warning flags on both compilers.
- Kernel log output is silenced in test runs unless `--verbose` is given
  (`--quiet-log` silences it again).

## 11. Error handling summary

| Situation | Mechanism |
|---|---|
| Programming error (invariant broken, bad argument) | `VAELEN_CHECK` / `VAELEN_CHECKF`, then guard |
| Recoverable, caller can continue | `VAELEN_ENSURE` + early return |
| Expected failure (table full, kind exhausted, unknown sink) | `bool` return or `Invalid()` value, documented in the header |
| Impossible path | `VAELEN_UNREACHABLE()` |
| Anything worth a human look | log at `Warning` or `Error` |

No exceptions, no error codes as globals (`errno`-style), no `std::optional`
in public APIs yet (allowed).

## 13. Kernel purity checker

`Tools/check_kernel_purity.py` (Python 3, standard library only) scans, for
every module in `Tools/kernel_modules.txt`, `Source/<M>/Public/**/*.h|*.inl`
and `Source/<M>/Private/**/*.cpp|*.h|*.inl`, skipping the single
`*Module.cpp`. Comments and string/character literals are blanked before
R1–R4 and R7; R5 and R6 read the raw text.

| Rule | Name | Checks | Exemptable |
|---|---|---|---|
| R0 | structure | at most one `*Module.cpp` per module; every `PURITY-ALLOW` comment well-formed | no |
| R1 | include-whitelist | `"Vaelen/..."` or a non-banned standard header | yes |
| R2 | no-exceptions | `throw`, `try {`, `catch (` | yes |
| R3 | no-rtti | `dynamic_cast`, `typeid` | yes |
| R4 | deterministic-random | `rand()/srand()`, `random_device`, `mt19937`, other `<random>` engines, `std::chrono`, clocks, `time()`, `clock()`, OS timers | yes |
| R5 | header-hygiene | `#pragma once` in `.h`; `// STATUS:` line with a valid value in `.h`/`.inl` (validated in `.cpp` when present) | yes |
| R6 | no-fake-done | `VALIDATED` file contains `TODO`, `FIXME` or "implement later" | yes |
| R7 | fixed-width | bare `long` family outside `static_cast<...>` | yes |

Exemption syntax — a trailing comment on the offending line:

```cpp
const long long Printable = static_cast<long long>(Value); // PURITY-ALLOW(R7): printf boundary
int Bits = rand(); throw 1;                                  // PURITY-ALLOW(R4, R2): reason for both
```

- Form: `// PURITY-ALLOW(Rn): reason`, or `// PURITY-ALLOW(Rn, Rm): reason`.
  The reason is mandatory; a missing reason, missing parentheses, unknown rule
  or `R0` is itself an R0 violation.
- File-level R5 findings (missing `#pragma once` or STATUS) accept the
  exemption on any line of the file.
- An exemption that exempts nothing is reported as a note under `--verbose`
  (not a failure); remove it.
- Exemptions are for genuine boundaries (printf casts, deliberate multi-include
  `.inl`), never for smuggling engine code or randomness into the kernel.

Running:

```
python3 Tools/check_kernel_purity.py --root . [--list] [--verbose]
python3 Tools/check_kernel_purity.py --self-test
```

Exit 0 and `[purity] N files, 0 violations` when clean; 1 with violations
listed as `path:line: Rn rule-name: message`; 2 on a configuration error.
Observed on 2026-09-05: `[purity] 12 files, 0 violations`; self-test
`32 checks, 0 failed`. Add every new kernel module to `Tools/kernel_modules.txt`
the moment it is created.

## 14. Process

### 14.1 Work protocol (master prompt §38)

```
PLAN → EXPLAIN → IMPLEMENT → TEST → VALIDATE → NEXT
```

Never jump to a large implementation. Each response (master prompt §67):
show the BUILD STATUS; explain what will be done; implement a reasonable
amount; list files created/modified; list tests; list problems; name the next
task. Never hide a limitation; never claim an untested result.

Decision rule (master prompt §62): when several solutions are reasonable,
prefer in order robustness, architectural simplicity, performance,
evolvability, determinism; explain the choice briefly; ask the user only for
decisions that are fundamental, irreversible or architecture-changing.

## 15. Quick checklist before a task is marked VALIDATED

1. Builds warning-free: `clang++` and `g++`, Debug (assertions on).
2. `ctest` green, including `Kernel.Purity`.
3. New headers: banner, STATUS, `#pragma once`, include order, `VAELENCORE_API`.
4. New system: unit, deterministic and edge-case tests exist; integration and
   long-duration tests exist or are explicitly listed as missing in the STATUS
   line.
5. No `TODO`/`FIXME` in `VALIDATED` files; no `PURITY-ALLOW` without a real
   reason.
6. Determinism: streams derived by name, no wall-clock, no order-dependent
   iteration, no undocumented float accumulation.
7. Progress report with the BUILD STATUS block, files, tests, problems, next.
